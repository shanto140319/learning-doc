Next.js (App Router) adds one big idea on top of React: code runs on the **server** and on the **client**, and data crosses between them. Most typing rules here are about that boundary.

## Pages and layouts: use the generated helpers

`params` and `searchParams` are **Promises** in current Next.js, so you `await` them. Next generates global helpers, `PageProps` and `LayoutProps`, typed from your real folder names:

```tsx
// app/[business]/book/[serviceId]/page.tsx
export default async function BookPage(props: PageProps<'/[business]/book/[serviceId]'>) {
  const { business, serviceId } = await props.params;   // both typed as string
  // ...
}
```

The types are generated by `next dev`, `next build` or `next typegen`. This project already has a script for it: `npm run types:check`.

## Search params are untrusted input

Search param values are `string | string[] | undefined`, and the user can type anything in the URL. Parse them:

```tsx
const SearchSchema = z.object({
  date: z.iso.date().optional(),                // "2027-01-10"
  page: z.coerce.number().int().min(1).default(1),
});

export default async function BookingsPage(props: PageProps<'/bookings'>) {
  const { date, page } = SearchSchema.parse(await props.searchParams);
}
```

## Server Actions: validate, then return a union

A Server Action is a public endpoint. Anyone can call it with any data, so the input must be validated. Return a discriminated union so the form can show the right message:

```tsx
'use server';

type ActionState =
  | { status: 'idle' }
  | { status: 'error'; fieldErrors: Record<string, string[] | undefined> }
  | { status: 'success'; bookingId: string };

export async function createBookingAction(
  _prev: ActionState,
  formData: FormData,
): Promise<ActionState> {
  const parsed = BookingRequestSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) {
    return { status: 'error', fieldErrors: z.flattenError(parsed.error).fieldErrors };
  }
  const booking = await bookings.create(parsed.data);
  return { status: 'success', bookingId: booking.id };
}
```

Also check **who** is calling (auth and tenant) inside every action, not only in the page.

## The server–client boundary

- Props passed from a Server Component to a `'use client'` component must be **serializable**. Functions (except Server Actions) and class instances can't cross.
- Add `import 'server-only'` to files that hold secrets or database code. Importing them into a client component then fails the build.
- Only `NEXT_PUBLIC_` env vars reach the browser. Validate env vars with Zod in two separate modules: one for the server, one for public values.

## Typed links

Turn on `typedRoutes: true` in `next.config.ts`. Then `<Link href="/bookngs">` is a type error, because that route doesn't exist.

## Common mistakes

- Typing `params` as a plain object (old Next.js style) instead of a Promise.
- Trusting `searchParams` or `FormData` without parsing.
- `await res.json()` in a Server Component with no schema. Its type is `any`.
- Doing the auth check in the page but not in the Server Action.

## Interview answer

**"How do you make a Server Action type-safe and secure?"**

> "I treat a Server Action like a public API endpoint. First I check the session and the user's permissions. Then I validate the `FormData` with a Zod schema, because TypeScript can't check data that comes from the browser. I return a discriminated union, like success or error with field errors, so the form handles every case with full type safety."
