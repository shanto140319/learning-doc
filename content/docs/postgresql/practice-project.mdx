Replace the in-memory repositories in your [NestJS practice project](/docs/nestjs/practice-project) with PostgreSQL and Prisma. The API stays the same from the outside. Inside, the database now guarantees the rules that matter, and you can **prove** it with a race test.

This project is the real foundation of Project 1, so do it properly. It's also your best interview story from Phase 1: "I made double bookings impossible with one Postgres constraint, and here's the test that proves it."

Time: one Friday block (about 4 hours) plus two or three weekday sessions.

## Requirements

### Endpoints

Everything from the NestJS project, plus:

| Endpoint | Who | Notes |
| --- | --- | --- |
| `GET /v1/staff/:id/availability?date=YYYY-MM-DD&serviceId=...` | Public | Free slots from working hours, service length and the business's time zone (exercise 3.4) |
| `PATCH /v1/bookings/:id` | Any logged-in user | Reschedule. `If-Match` required, 412 on version mismatch, 409 `slot-taken` on overlap |
| `GET /v1/reports/daily?from=...&to=...` | owner, admin | Bookings and revenue per day in the business's time zone, with zero days (Lesson 7) |

### Quality checklist

- [ ] Prisma 7 with the driver adapter, `prisma.config.ts`, `@db.Timestamptz` on every `DateTime`
- [ ] Custom SQL migration: `bookings_no_overlap` exclusion constraint, check constraints, partial unique index for service names, `lock_timeout` at the top
- [ ] `staff_working_hours` table with constraints (exercise 2.4)
- [ ] `PrismaService` in a global `DatabaseModule`; readiness check runs `select 1`
- [ ] Repositories are the only classes that use Prisma; controllers and services don't change much from the NestJS project
- [ ] Every query is scoped by `businessId`; composite foreign keys in the schema
- [ ] `GET /v1/bookings` uses keyset pagination with `select` (no N+1, check the query log)
- [ ] `POST /v1/bookings` runs in one transaction: customer upsert, booking insert, outbox event
- [ ] Overlap → 409 `slot-taken`; not found → 404; no Prisma error ever reaches the client as a 500 with internal details
- [ ] Idempotency keys stored in Postgres with `on conflict do nothing` (scaffold below)
- [ ] Optimistic locking on reschedule with `version`, `ETag` and `If-Match`
- [ ] Cancel writes an outbox event in the same transaction
- [ ] Seed script that's safe to run twice
- [ ] App connects as `booking_app`; migrations run as `booking_migrator`
- [ ] Pool size, `connectionTimeoutMillis` and `statement_timeout` set on purpose (write the numbers and why in the README)
- [ ] **Race test** passes (scaffold below)
- [ ] `PERFORMANCE.md` (see below)
- [ ] Stretch: row-level security with the `forTenant` extension (Lesson 10)

## Test checklist

Run the [NestJS project's checks](/docs/nestjs/practice-project#test-checklist) again (they must still pass), plus:

1. Restart the app: data is still there.
2. `npm run race` (or the script): exactly one 201 and nineteen 409s, every time you run it.
3. Book 10:00–10:30, then 10:30–11:00 for the same staff member: both succeed.
4. Cancel the 10:00 booking, book 10:00 again: succeeds.
5. Same `Idempotency-Key` twice at the same moment (two terminals or `Promise.all`): one booking, both responses have the same ID (or the second gets 409 "still processing").
6. Reschedule with an old `If-Match`: 412. With the right one: 200, and the `ETag` changes.
7. After create and cancel, the `outbox` table has the matching events.
8. Availability for a day with existing bookings: those slots are missing; a lunch break has no slots.
9. Run `prisma db seed` twice: no errors, no duplicates.
10. As `booking_app` in `psql`: `drop table bookings;` fails.
11. With `log: ['query']`, `GET /v1/bookings` runs 1 or 2 queries, not 21.
12. Stretch: remove the `businessId` filter from one query; RLS still hides other businesses' rows.
