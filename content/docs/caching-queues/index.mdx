So far, every request to the booking API does all its work **while the user waits**, and every request goes to Postgres. That's fine for one user. It stops being fine when:

- the public booking page gets 500 visitors a minute, and each one runs the availability query;
- sign-up takes 3 seconds because the email server is slow, or **fails** because it's down;
- a reminder must be sent 24 hours before each booking, and nobody is making a request at that moment;
- the API runs on 3 servers, and the rate limiter on each one counts separately.

This section adds the two tools almost every production backend has: a **cache** (Redis) and a **job queue** (BullMQ, which also runs on Redis). All examples extend the **booking API** from the [Testing practice project](/docs/testing/practice-project) (NestJS + Prisma 7 + PostgreSQL 18).

## Setup

In the **booking API**:

```powershell
npm i ioredis bullmq @nestjs/bullmq @nest-lab/throttler-storage-redis
npm i @bull-board/api @bull-board/express @bull-board/nestjs
npm i -D @testcontainers/redis
```

Add Redis to `docker-compose.yml` (Lesson 2 explains each setting; Lesson 8 splits it into two instances):

```yaml
services:
  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes", "--maxmemory-policy", "noeviction"]
    ports:
      - "127.0.0.1:6379:6379"
    volumes:
      - redis-data:/data

volumes:
  redis-data:
```

And to `.env`: `REDIS_URL=redis://localhost:6379`.

Scripts you'll have at the end of the section:

```json
{
  "scripts": {
    "start:dev": "nest start --watch",
    "start:worker:dev": "nest start --watch --entryFile worker",
    "start:worker": "node dist/worker"
  }
}
```

<Callout type="warn" title="Versions">
Written for Redis 8, ioredis 5, BullMQ 5, `@nestjs/bullmq` 11 and Bull Board 6. BullMQ changes faster than most libraries: for example, `upsertJobScheduler` replaced the older `repeat` option for recurring jobs, and many blog posts still show the old way or the even older `bull` package (without "mq"). When an example doesn't match, check the BullMQ docs at docs.bullmq.io first.
</Callout>

## How each lesson works

Same as before: type the examples yourself, do the exercises without help, send them to Claude for a scored review, then check the [Solutions](/docs/caching-queues/solutions). Write your mistakes in each page's notes box and practise the interview answers out loud.

Background work has one extra rule: **break it on purpose**. Stop Redis, kill the worker in the middle of a job, stop Mailpit. Watch what happens. The goal of this section is that nothing is lost and nothing is sent twice (or, where "twice" can't be fully prevented, that you know exactly when and why).
