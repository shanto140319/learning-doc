A well-designed API is boring in a good way: once a developer learns one endpoint, they can guess the rest. This lesson gives you the rules that most companies follow, and ends with a complete API design for the booking platform.

## Resources and URLs

REST thinks in **resources** (things: bookings, services, staff), and uses **HTTP methods as the verbs**.

| Rule | ✅ Good | ❌ Avoid |
| --- | --- | --- |
| Nouns, not verbs | `POST /bookings` | `POST /createBooking` |
| Plural collections | `GET /services`, `GET /services/s1` | `GET /service/s1` |
| Lowercase, words joined with hyphens | `/time-slots` | `/timeSlots`, `/time_slots` |
| IDs in the path, options in the query | `GET /bookings?status=confirmed` | `GET /bookings/confirmed` |
| Nest only one level, for real ownership | `GET /services/s1/bookings` | `GET /businesses/b1/services/s1/bookings/b9/notes` |
| No file extensions | `GET /bookings/b1` | `GET /bookings/b1.json` |

The standard five endpoints for a resource:

| Method and path | Meaning | Success status |
| --- | --- | --- |
| `GET /bookings` | List (with pagination, Lesson 7) | `200` |
| `POST /bookings` | Create | `201` + `Location` header + the new object |
| `GET /bookings/:id` | Get one | `200` |
| `PATCH /bookings/:id` | Change some fields | `200` + the updated object |
| `DELETE /bookings/:id` | Delete | `204` (no body) |

### Actions that don't fit CRUD

Some operations are not "create, read, update, delete". Cancelling a booking has rules (only before the start time, send an email, maybe refund). Two acceptable styles:

```text
POST /bookings/b1/cancel         ← an action sub-resource (clear, popular; Stripe uses it)
PATCH /bookings/b1  {"status":"cancelled"}   ← a state change
```

Prefer the action style when the operation has side effects (emails, refunds) or rules. A plain `PATCH` of `status` makes it too easy to skip the rules.

### Who is "me"?

For multi-tenant apps, don't put the business ID from the client in every URL and trust it. The logged-in user's token says which business they belong to. Use routes like `GET /me` and `GET /bookings`, and **always scope the database query to the user's business on the server** (Month 2, multi-tenancy).

## JSON conventions

Pick one style and use it everywhere:

- Field names in **camelCase** (`startsAt`, `customerEmail`). It's the JavaScript/TypeScript norm. (Some APIs use snake_case, like Stripe. Either is fine; mixing is not.)
- Dates as **ISO 8601 strings in UTC**: `"2026-11-03T10:00:00Z"`. Never local time without an offset. Time zones are a big topic in Project 1.
- Money as **integer minor units plus currency**: `{ "amountCents": 150000, "currency": "BDT" }`. Never floats (`0.1 + 0.2 !== 0.3`).
- IDs as **strings**, even if they're numbers in the database. Clients shouldn't do maths on IDs, and you can change ID format later.
- Return the **full object** after create and update, so the client doesn't need a second request.
- Wrap lists in an object: `{ "data": [...], "nextCursor": "..." }`, never a bare array. You can add fields later without breaking clients.

## Status codes: which one when

You don't need all 60. These cover 99% of real APIs:

| Code | Name | Use it when |
| --- | --- | --- |
| `200` | OK | Successful GET, PATCH, or an action that returns data |
| `201` | Created | POST created something. Add a `Location` header |
| `202` | Accepted | Work was queued and will finish later (report generation) |
| `204` | No Content | Success with no body (DELETE) |
| `301` / `308` | Moved Permanently | A URL changed for good (`308` keeps the method and body) |
| `302` / `307` | Found / Temporary Redirect | Temporary redirect, like a URL shortener (`307` keeps the method) |
| `304` | Not Modified | The client's cached copy is still valid (ETag) |
| `400` | Bad Request | The request is broken: invalid JSON, wrong query parameter type |
| `401` | Unauthorized | **Not logged in**: no token, or the token is invalid or expired |
| `403` | Forbidden | **Logged in but not allowed**: staff trying to delete the business |
| `404` | Not Found | The resource doesn't exist, **or the user isn't allowed to know it exists** |
| `405` | Method Not Allowed | Route exists, method doesn't. Add an `Allow` header |
| `409` | Conflict | Clashes with the current state: slot already taken, email already registered |
| `413` | Payload Too Large | Body over the limit |
| `415` | Unsupported Media Type | Wrong `Content-Type` |
| `422` | Unprocessable Content | Valid JSON, but the values fail validation: email missing, date in the past |
| `429` | Too Many Requests | Rate limit hit. Add `Retry-After` |
| `500` | Internal Server Error | A bug or unexpected failure |
| `502` | Bad Gateway | An upstream service (Stripe, email API) returned an error |
| `503` | Service Unavailable | Temporarily down: maintenance, overload. Add `Retry-After` |
| `504` | Gateway Timeout | An upstream service didn't respond in time |

Quick decision rules:

- **4xx = the client must change something. 5xx = the server's fault; retrying later may work.** Clients and monitoring tools rely on this split.
- **400 vs 422:** many teams use `400` for all bad input, and that's fine. If you separate them: `400` when the request can't even be read, `422` when it's readable but the values are wrong. NestJS's default `ValidationPipe` uses `400`. Choose one rule and write it down.
- **401 vs 403:** "Who are you?" vs "I know who you are, and the answer is no."
- **403 vs 404 for other tenants' data:** if business A asks for business B's booking, return `404`. A `403` confirms that the booking ID exists, which leaks information.
- **Never return `200` with `{ "success": false }`.** Clients, caches, logs and monitoring all trust the status code.

## One consistent error format

Every error from every endpoint should have **the same shape**, so the frontend can handle errors with one function. A good standard is **RFC 9457 "Problem Details"** (it replaced RFC 7807). A simplified version:

```typescript
// shared/api-error.ts — shared by the backend and the Next.js frontend
export type ApiError = {
  type: string;        // a stable code or URL: "slot-taken"
  title: string;       // short, human-readable: "Time slot unavailable"
  status: number;      // repeats the HTTP status: 409
  detail?: string;     // this specific case: "Check-up at 10:00 on 3 Nov is already booked"
  instance?: string;   // the request path: "/v1/bookings"
  requestId?: string;  // for support: "Please quote this ID"
  errors?: Array<{ field: string; message: string }>; // validation details
};
```

A validation error:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "validation-failed",
  "title": "Your request has invalid fields",
  "status": 422,
  "requestId": "f3c1a9e2-6c0b-4f0b-9d8e-2a4b7c1e5d10",
  "errors": [
    { "field": "startsAt", "message": "Must be in the future" },
    { "field": "email", "message": "Must be a valid email address" }
  ]
}
```

Rules:

- The `type` (or `code`) is for **programs**: the frontend checks `if (err.type === 'slot-taken')`. It never changes. The `title` and `detail` are for **humans** and may change.
- Return **all** validation errors at once, not only the first. Users hate fixing one field at a time.
- Never include stack traces, SQL, or internal hostnames.

This connects with Lesson 3: each `AppError` subclass maps to one `type` and status, in one central error handler.

## Versioning

Once other people use your API (a mobile app, a partner, a public API), you can't change it freely. Old app versions stay installed on phones for years.

**Breaking changes** (need a new version): removing or renaming a field, changing a field's type or meaning, making an optional input required, changing the error format, removing an endpoint.

**Non-breaking changes** (no new version): adding a new endpoint, adding a new optional input field, adding a new field to a response. This is why clients must **ignore fields they don't know**.

Ways to version:

| Style | Example | Notes |
| --- | --- | --- |
| **URL path** | `/v1/bookings` | Most common. Easy to see, test and route. **Use this by default.** |
| Header | `Accept: application/vnd.bookly.v2+json` | Cleaner URLs, harder to test in a browser |
| Date-based | `Stripe-Version: 2026-10-01` | Stripe's approach. Powerful, complex to build |

In practice: start with `/v1`, avoid breaking changes by only **adding** things, and create `/v2` only for big redesigns. When you retire an old version, announce a date and send a `Deprecation` or `Sunset` header first.

For an API used only by your own Next.js frontend, deployed together, you often don't need versions at all. Add `/v1` anyway; it's free and keeps your options open.

## The booking platform API (first version)

```text
Auth
  POST   /v1/auth/register
  POST   /v1/auth/login
  POST   /v1/auth/refresh
  GET    /v1/me

Services (owner/admin can write; staff can read)
  GET    /v1/services
  POST   /v1/services
  GET    /v1/services/:id
  PATCH  /v1/services/:id
  DELETE /v1/services/:id

Availability and slots
  GET    /v1/staff/:id/availability
  PUT    /v1/staff/:id/availability          ← replace the whole weekly schedule
  GET    /v1/services/:id/slots?date=2026-11-03&timezone=Asia/Dhaka

Bookings
  GET    /v1/bookings?status=confirmed&from=...&to=...&cursor=...&limit=20
  POST   /v1/bookings                         ← requires Idempotency-Key (Lesson 7)
  GET    /v1/bookings/:id
  POST   /v1/bookings/:id/cancel
  POST   /v1/bookings/:id/reschedule
  GET    /v1/bookings/export                  ← CSV stream (Lesson 4)
```

Notice `PUT` for availability: the client sends the whole weekly schedule, and the server replaces it. That's simpler and idempotent, compared with many small `PATCH` calls.

## Common mistakes

- Verbs in URLs for normal CRUD: `/getBookings`, `/deleteService`.
- Returning `200` for errors, or `500` for user mistakes.
- A different error shape from each endpoint (one returns `message`, another `error`, a third `errors[]`).
- Returning a bare array from list endpoints.
- Leaking other tenants' data existence with `403`.

## Interview answer

**"What makes a good REST API?"**

> "Consistency and predictability. I model resources as plural nouns and use HTTP methods as verbs, with correct status codes: 201 for create, 4xx when the client has to change something, 5xx for server problems. Every error has the same shape, with a stable machine-readable code, a human message and field-level validation errors, and no internal details. Lists are paginated and wrapped in an object. I version with `/v1` in the path and avoid breaking changes by only adding fields. And for operations like payments, I make POST requests safe to retry with idempotency keys."

**"When do you use 401 vs 403?"**

> "401 means the server doesn't know who you are: the token is missing, invalid or expired, so the client should log in again. 403 means the server knows who you are, but you're not allowed to do this. One exception: if a user asks for a resource from another tenant, I return 404 instead of 403, so I don't reveal that the resource exists."
