Until now, you checked your booking API by hand: run a `curl`, look at the response, run the race script. That works once. It doesn't work after the 50th change, when you can't remember everything that used to work.

Automated tests let you **change code without fear**. They're also part of what makes a project look professional: a CI badge, a `test` folder and a race test you can show an interviewer say "this person ships production code".

All examples test the **booking API** from the [Auth and security practice project](/docs/auth-security/practice-project) (NestJS + Prisma 7 + PostgreSQL 18), plus a small Next.js frontend for Lessons 6 and 7.

## Before you start

Finish the [Auth and security practice project](/docs/auth-security/practice-project) first, or at least Lessons 1–6 of that section: the tests here log in with real sessions and check roles and tenants.

You also need **Docker Desktop running**. Testcontainers (Lesson 3) starts a real PostgreSQL in Docker for your tests.

### Topics added beyond the roadmap

The roadmap lists Jest unit tests with mocked providers, integration tests on a real Postgres in Docker (Testcontainers), e2e tests with Supertest, and Playwright for critical user flows. All of them are covered.

These are added because **your projects need them** or **interviews ask about them**:

| Added topic | Why | Lesson |
| --- | --- | --- |

| Typed mocks, testing guards and pipes, pure policy functions | Your security code (Auth section) needs tests most | 2 |
| **Test data factories** and resetting the database | Without them, database tests get slow and flaky | 3 |

| React component tests (React Testing Library) | You're a frontend engineer; frontend interviews ask about it | 6 |
| Playwright: saved login, network mocking, **accessibility checks** with axe, traces | Makes browser tests fast, stable and useful | 7 |

## Setup

In the **booking API** (NestJS already installed Jest, `ts-jest`, `@nestjs/testing` and Supertest when you created the project). Add the rest:

```powershell
npm i -D @testcontainers/postgresql msw @faker-js/faker
```

In the **Next.js frontend** (Lessons 6 and 7):

```powershell
npm i -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom vite-tsconfig-paths msw
npm init playwright@latest
npm i -D @axe-core/playwright
```

Scripts you'll have at the end of the section, in the API's `package.json`:

```json
{
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:int": "jest --config test/jest-int.json",
    "test:cov": "jest --coverage",
    "test:all": "npm test && npm run test:int"
  }
}
```

<Callout type="warn" title="Versions">
Written for Jest 30, Testcontainers 11, MSW 2, Vitest 4 and Playwright 1.5x. Tests rarely break between minor versions, but if an import doesn't exist, check the tool's own docs before asking an AI: older answers often show older APIs (for example MSW 1's `rest.get` instead of MSW 2's `http.get`).
</Callout>

## How each lesson works

Same as before: type the examples yourself, do the exercises without help, send them to Claude for a scored review, then check the [Solutions](/docs/testing/solutions). Write your mistakes in each page's notes box and practise the interview answers out loud.

Testing has one extra rule: **see every test fail once**. After a test passes, break the code on purpose (change `>` to `>=`, remove a `where`, delete a guard) and check the test goes red. A test that has never failed might not be testing anything.
