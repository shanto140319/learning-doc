## Lesson 1: Why test, what to test, Jest basics

**1.1**

| Feature | First test | Why |
| --- | --- | --- |
| (a) `freeSlots` | Unit | A pure function: fast, many cases, no dependencies |
| (b) The exclusion constraint | Integration (real Postgres) | The rule lives in the database; only a real database can prove it |
| (c) 404 for another business's booking | API test | It depends on the guard, the query and the filter together, through HTTP |
| (d) "Book" disabled while sending | Component test | A UI state; Testing Library + MSW with a small delay |
| (e) Sign-up → verify → log in | Browser (Playwright), plus an API test of the same flow | Crosses pages, email and cookies; the API test is faster and catches most bugs, the browser test proves the pages work |
| (f) Refresh token reuse detection | API test (plus integration tests for the repository) | It's about cookies, the database and timing together |

**1.2** Typical results:

- `<` → `<=` in `overlaps`: the "touching ends" row fails, in both directions. The `freeSlots` tests still pass, because none of their bookings touch a slot edge. That shows a gap: add a `freeSlots` test where a booking ends exactly when a slot starts.
- `t + step <= end` → `<`: "returns every slot when nothing is booked" fails (the 10:30 slot, which ends exactly at closing time, disappears). "Does not return a slot that would end after closing" still passes, which shows why you need **both** edge tests.
- Removing the `durationMin` check: "throws for a zero-length service" doesn't fail, it **hangs forever**, because `t += 0` loops and Jest's timeout can't stop a synchronous loop. So the check protects against a frozen server, not just a wrong answer.

If a change went unnoticed, you've found a missing test. That's the point of the exercise.

**1.4** In the NestJS Lesson 2 tests:

- `expect(booking.status).toBe('confirmed')`: **behaviour**.
- `rejects.toThrow(ConflictException)`: **behaviour**.
- `expect(repo.insert).not.toHaveBeenCalled()` after the conflict: **behaviour** (nothing was saved when the rule failed).
- `expect(repo.insert).toHaveBeenCalledTimes(1)` in the success test: borderline. It's "the booking was saved", which is behaviour. A better version checks **what** was saved: `expect(repo.insert).toHaveBeenCalledWith(expect.objectContaining({ status: 'confirmed', startsAt: ... }))`.
- Anything like `expect(repo.findAt).toHaveBeenCalledWith(...)`: **implementation**. Delete it; if the lookup were wrong, the result tests would fail.

**3.2** Dropping the constraint in a migration (`alter table bookings drop constraint bookings_no_overlap;`) makes exactly one test fail: "rejects an overlapping booking". **5.2**

- **Spring forward (2027-03-14), 01:00–04:00:** 4 slots (06:00, 06:30, 07:00, 07:30 UTC), as in the lesson. A common bug: generating local times 01:00, 01:30, 02:00, 02:30, 03:00, 03:30 and converting each. Postgres turns the non-existent 02:00 and 02:30 into 03:00 and 03:30 EDT, so you get **duplicate** slots. The fix: convert the opening and closing times to `timestamptz` first, then step through UTC.
- **Fall back (2027-11-07):** with working hours 00:00–03:00, the day is **4** real hours long (00:00 EDT = 04:00Z to 03:00 EST = 08:00Z), so there are 8 slots: 04:00, 04:30, 05:00, 05:30, 06:00, 06:30, 07:00, 07:30 UTC. On a New York clock they read 00:00, 00:30, 01:00, 01:30, **01:00, 01:30**, 02:00, 02:30. The UI must show which 01:00 is which (for example "1:00 AM EDT" and "1:00 AM EST"). Avoid working hours that start or end inside the repeated hour in tests: Postgres resolves an ambiguous local time to one side, and the test then depends on that choice.
- **"Today" in Dhaka at 2026-12-01T23:30Z:** Dhaka's today is December 2, which is `[2026-12-01T18:00Z, 2026-12-02T18:00Z)`. A booking at `2026-12-01T17:00Z` (23:00 on Dec 1 in Dhaka) is **not** today; one at `2026-12-01T20:00Z` (02:00 on Dec 2) **is**. A version that uses the UTC date gets both wrong.

**5.4** The last-owner version of the two-connection test:

```typescript
it('makes the second owner removal wait for the first, then refuse', async () => {
  const business = await f.business();
  const ownerA = await f.member(business.id, 'owner');
  const ownerB = await f.member(business.id, 'owner');
  const [a, b] = [new Client({ connectionString: process.env.DATABASE_URL }), new Client({ connectionString: process.env.DATABASE_URL })];
  await Promise.all([a.connect(), b.connect()]);
  const { rows: [{ pid: bPid }] } = await b.query<{ pid: number }>('select pg_backend_pid() as pid');

  const lockOwners = (c: Client) =>
    c.query(`select user_id from memberships where business_id = $1 and role = 'owner' for update`, [business.id]);

  try {
    await a.query('begin');
    await lockOwners(a);                                          // A sees 2 owners and locks them

    await b.query('begin');
    const bLock = lockOwners(b);                                  // B must wait
    await eventually(async () => {
      const { rows } = await a.query('select wait_event_type from pg_stat_activity where pid = $1', [bPid]);
      expect(rows[0]?.wait_event_type).toBe('Lock');
    });

    await a.query(`delete from memberships where business_id = $1 and user_id = $2`, [business.id, ownerB.id]);
    await a.query('commit');

    const { rows } = await bLock;                                 // B wakes up and re-reads the locked rows
    expect(rows).toHaveLength(1);                                 // only one owner left → the code must refuse
  } finally {
    await b.query('rollback').catch(() => {});
    await Promise.all([a.end(), b.end()]);
  }
});
```

This test checks the **SQL pattern** your service uses. Without `for update`, B doesn't wait: the `eventually` check fails every run, because B's `select` returns immediately with two owners. (For a full check of your service code, run `members.remove` for B while A holds the lock, using the same idea.)

## Lesson 7: Playwright

**7.1** Your trace shows the `goto`, each `fill`, the click, the network calls to `/v1/auth/login` (with `Set-Cookie`) and the dashboard request. If the setup test passes but the reload test shows the login page, check that the `access_token` cookie is in `playwright/.auth/owner.json` and that its `domain` is `localhost`.

**7.2** The usual failure with `--repeat-each=10`: two runs at the same time pick the **same first free slot**, one books it, and the other gets "that time was just taken", or its "slot is gone" check fails because another run's booking also removed a slot. Fixes, best first: give each test its own staff member or service (create them through the API in a fixture), or pick a different day per run (`testInfo.workerIndex` and `testInfo.repeatEachIndex` in the date). Don't fix it with `workers: 1`: the test would still break when the suite grows.

**7.3** Common axe findings in a fresh Next.js app: `color-contrast` on grey helper text, `label` on an input with only a placeholder, `button-name` on an icon-only button (add `aria-label`), `landmark-one-main` (wrap the page content in `<main>`), and `region` (content outside landmarks). Fix them in the components, not with `disableRules`.

## Lesson 8: CI, coverage, flaky tests

**8.1** On a PR, the "checks" job fails and shows the failing test's name and diff in the log. With branch protection, the "Merge" button is greyed out until it's green. (Admins can bypass by default: turn on "Do not allow bypassing the above settings" if you want the rule to apply to you too.)

**8.2** Yes, keeping `--randomize` in CI is a good idea for the integration suite, **because Jest prints the seed**: when a random order fails, you copy the seed from the log and reproduce it locally with `--seed`. The cost is that a failure might not show up on every run, so read the seed in every red run instead of re-running. Some teams randomize only on a nightly run for this reason; both are fine.

**8.3** Red lines that matter: the reuse-detection branch in `refresh()`, the "not a member" branch in `MembershipGuard`, the `ALREADY_CANCELLED` branch, the error-mapping branch for the exclusion constraint. Red lines that don't: `main.ts`, module files, the `SystemClock` class, a `toString` in a DTO. Note that some "red" lines in the **unit** report are green in the **integration** report: check both before writing a test.

**8.4** In the trace you see: the page loads, the 300 ms wait ends, the test reads the slot list while the availability request is still pending (it took 450 ms on that run), so it finds no button, and the click times out. On the retry, the request took 200 ms and the test passed, so the report says "flaky". The fix: delete the `waitForTimeout` and wait for the result instead, with `await expect(day.getByRole('button').first()).toBeVisible()` before reading it. Then remove the random delay from the app.
