Every system that stores passwords will one day have its database stolen: through a bug, a leaked backup or a bad employee. The question is what the attacker can do **then**. If you stored passwords correctly, the answer is "almost nothing". This lesson shows you how.

## Hashing, not encryption

| | Encryption | Hashing |
| --- | --- | --- |
| Reversible? | Yes, with the key | No, one way only |
| If the database leaks | The attacker looks for the key (often in the same server) and reads every password | The attacker must **guess** each password and hash each guess |
| Use for passwords? | **Never** | **Yes**, with a slow password hash |

To check a login, you don't need the password back. You hash what the user typed and compare it with the stored hash.

But a normal hash like SHA-256 is **too fast**. A gaming GPU computes billions of SHA-256 hashes per second, so an attacker can try every common password against every user in minutes. A password hash must be:

1. **Salted:** a random value per password, stored with the hash. Two users with the password `dhaka2026` get different hashes, so the attacker can't crack everyone at once or use precomputed tables.
2. **Slow and memory-hungry:** each guess costs time **and** memory, which makes GPU attacks expensive.

| Algorithm | Use it? |
| --- | --- |
| **argon2id** | **Yes**, the current recommendation (OWASP). Slow and memory-hard |
| bcrypt | OK for existing systems. Only uses the first 72 bytes of the password |
| scrypt | OK; built into Node (`crypto.scrypt`) |
| PBKDF2 | Only when a rule (FIPS) requires it |
| MD5, SHA-1, SHA-256 (alone) | **Never** for passwords |

## argon2id in NestJS

```powershell
npm i argon2
```

The `argon2` package uses native code but ships prebuilt binaries for Windows, macOS and Linux, so it normally installs without a compiler.

```typescript
// src/auth/password.service.ts
import { Injectable, OnModuleInit } from '@nestjs/common';
import * as argon2 from 'argon2';

// OWASP's minimum for argon2id: 19 MiB memory, 2 iterations, 1 thread.
// Raise memoryCost if your server can afford it (measure: exercise 1.1).
const OPTIONS = {
  type: argon2.argon2id,
  memoryCost: 19_456,   // in KiB = 19 MiB
  timeCost: 2,
  parallelism: 1,
} as const;

@Injectable()
export class PasswordService implements OnModuleInit {
  private dummyHash = '';

  async onModuleInit(): Promise<void> {
    // Used when the email doesn't exist, so "no such user" takes as long as "wrong password"
    this.dummyHash = await argon2.hash('dummy-password-for-timing', OPTIONS);
  }

  hash(password: string): Promise<string> {
    return argon2.hash(password, OPTIONS);   // creates a random salt for you
  }

  async verify(hash: string | null, password: string): Promise<boolean> {
    try {
      return await argon2.verify(hash ?? this.dummyHash, password);
    } catch {
      return false;    // a corrupted hash in the DB must not become a 500 with details
    }
  }

  needsRehash(hash: string): boolean {
    return argon2.needsRehash(hash, OPTIONS);   // true if it was made with older, weaker settings
  }
}
```

A stored hash looks like this:

```text
$argon2id$v=19$m=19456,t=2,p=1$hX9Xk3l1n2c0UQ...$5c2Vh0T9...
          version  settings     salt              hash
```

The algorithm, settings and salt are **inside** the string. That's why `verify` needs no extra input, and why you can raise the settings later without breaking old users (see "Upgrading hashes" below).

<Callout type="warn" title="Hashing costs memory">
Each hash uses about 19 MiB of RAM for a fraction of a second. 50 login requests at once need about 1 GB. A login endpoint without rate limiting is an easy way to knock your server over (Lesson 8). Hashing also runs on libuv's thread pool (4 threads by default), so many logins at once queue up.
</Callout>

## Password policy: what the experts say now

The old rules ("one uppercase, one number, one symbol, change it every 90 days") made passwords **worse**: people choose `Password1!` and then `Password2!`. NIST's current guidance (SP 800-63B):

| Rule | Why |
| --- | --- |
| **Minimum 15 characters** when the password is the only factor (8 if the account has 2FA) | Length beats complexity |
| Maximum at least 64 characters; **set a max** (for example 128) | Allow passphrases, but stop someone sending a 1 MB "password" to burn your CPU |
| **No composition rules** (no "must contain a symbol") | They don't help and they annoy users |
| **Check against breached passwords** | `qwerty123456789` is long but in every attacker's list |
| No forced rotation; change only after a breach | Forced changes lead to predictable patterns |
| Allow paste and password managers | Password managers create the best passwords |

For Project 1, a sensible choice: **minimum 12** characters for now (a friendlier start, and you'll add 2FA in Lesson 9), maximum 128, plus the breached-password check. Write your reason in the README. Interviewers like a reason more than a number.

### The breached-password check without sending the password

[Have I Been Pwned](https://haveibeenpwned.com/API/v3#PwnedPasswords) has hundreds of millions of leaked passwords. Its "range" API uses **k-anonymity**: you send only the first 5 characters of the password's SHA-1 hash, and it returns every leaked hash that starts with them. The service never sees the password or even the full hash.

```typescript
// src/auth/breached-password.ts
import { createHash } from 'node:crypto';

export async function isBreachedPassword(password: string): Promise<boolean> {
  const sha1 = createHash('sha1').update(password).digest('hex').toUpperCase();
  const prefix = sha1.slice(0, 5);
  const suffix = sha1.slice(5);

  try {
    const res = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`, {
      headers: { 'Add-Padding': 'true' },          // hides the real response size from network observers
      signal: AbortSignal.timeout(2_000),
    });
    if (!res.ok) return false;                      // fail open: don't block sign-up when the API is down
    const body = await res.text();
    return body.split('\n').some((line) => {
      const [hashSuffix, count] = line.trim().split(':');
      return hashSuffix === suffix && Number(count) > 0;   // padding lines have count 0
    });
  } catch {
    return false;
  }
}
```

SHA-1 is fine here: it's not storing anything, it's only the lookup key the API expects.

## The tables

The PostgreSQL section left users and memberships out of Prisma ("they come with auth"). Add them now:

```prisma
enum Role {
  owner
  admin
  staff

  @@map("role")
}

model User {
  id              String    @id @default(dbgenerated("uuidv7()")) @db.Uuid
  email           String    @unique                                 // always stored lowercase
  name            String
  passwordHash    String?   @map("password_hash")                   // null for Google-only accounts (Lesson 5)
  emailVerifiedAt DateTime? @map("email_verified_at") @db.Timestamptz(3)
  createdAt       DateTime  @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt       DateTime  @updatedAt @map("updated_at") @db.Timestamptz(3)

  memberships Membership[]

  @@map("users")
}

model Membership {
  businessId String   @map("business_id") @db.Uuid
  userId     String   @map("user_id") @db.Uuid
  role       Role
  createdAt  DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  business Business @relation(fields: [businessId], references: [id], onDelete: Cascade)
  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@id([businessId, userId])
  @@index([userId])                 // "which businesses am I in?"
  @@map("memberships")
}
```

Add `memberships Membership[]` to the `Business` model too. Then create the migration with `--create-only` and add the checks Prisma can't express:

```sql
alter table users add constraint users_email_lowercase check (email = lower(email));
alter table users add constraint users_name_length check (length(name) between 1 and 100);
```

Why `passwordHash` is nullable: a user who signs up with Google has no password. Your login code must treat `null` as "no password login for this account", not crash.

## Sign-up without leaking accounts

**User enumeration** means an attacker can find out whether an email has an account. Why it matters: a list of your real customers is useful for phishing ("Your booking was cancelled, click here"), for credential stuffing (Lesson 8), and in some products just **having an account** is private (a clinic, a therapist).

Where it leaks:

| Place | Leaky | Safe |
| --- | --- | --- |
| Login | "No account with this email" vs "Wrong password" | Always "Invalid email or password" |
| Login timing | Unknown email answers in 2 ms, known email in 80 ms (hashing) | Verify against a dummy hash when the user doesn't exist (`PasswordService.verify(null, ...)`) |
| Sign-up | "This email is already registered" | Always "Check your email to continue"; the email itself says what to do |
| Password reset | "No account found" | Always "If an account exists, we sent a link" (Lesson 4) |

The safe sign-up flow:

```text
POST /v1/auth/signup  { email, name, password }
  → always 202 "Check your email to continue"
  new email      → create user (unverified) → send "Verify your email" link
  existing email → create nothing           → send "You already have an account. Log in or reset your password."
```

The cost is a little friction: the user must open their inbox before they can log in. Many products accept enumeration on sign-up for a smoother experience and protect it with rate limiting instead. Both are valid; **choose on purpose** and say why.

```typescript
// src/auth/dto/signup.dto.ts (class-validator, like NestJS Lesson 5)
export class SignupDto {
  @Transform(({ value }) => (typeof value === 'string' ? value.trim().toLowerCase() : value))
  @IsEmail()
  @MaxLength(254)
  email!: string;

  @IsString()
  @Length(1, 100)
  name!: string;

  @IsString()
  @Length(12, 128)            // max length stops very long inputs reaching argon2
  password!: string;
}
```

```typescript
// src/auth/accounts.service.ts
@Injectable()
export class AccountsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly passwords: PasswordService,
    private readonly emails: AuthEmails,            // Lesson 4; log to the console for now
  ) {}

  async signup(dto: SignupDto): Promise<void> {
    if (await isBreachedPassword(dto.password)) {
      throw new BadRequestException('This password has appeared in a data breach. Please choose another one.');
    }

    const passwordHash = await this.passwords.hash(dto.password);   // slow work before touching the DB
    try {
      const user = await this.prisma.user.create({
        data: { email: dto.email, name: dto.name, passwordHash },
      });
      await this.emails.sendVerifyEmail(user);
    } catch (err) {
      if (isUniqueViolation(err)) {                 // P2002 (PostgreSQL Lesson 8): the email exists
        await this.emails.sendAlreadyRegistered(dto.email);
        return;                                     // same 202 as success
      }
      throw err;
    }
  }
}
```

Notice: there's no "does this email exist?" query before the insert. The unique constraint answers that question **and** handles two sign-ups for the same email at the same moment (the race from PostgreSQL Lesson 6).

The breached-password message is fine to show: it's about the password, not about any account.

## Login

```typescript
// in AccountsService
async verifyCredentials(email: string, password: string): Promise<User> {
  const user = await this.prisma.user.findUnique({ where: { email: email.trim().toLowerCase() } });

  // Always run verify, even with no user: same timing either way
  const ok = await this.passwords.verify(user?.passwordHash ?? null, password);
  if (!user || !user.passwordHash || !ok) {
    throw new UnauthorizedException('Invalid email or password');
  }
  if (!user.emailVerifiedAt) {
    throw new ForbiddenException('Please verify your email first');   // see the note below
  }

  if (this.passwords.needsRehash(user.passwordHash)) {
    const passwordHash = await this.passwords.hash(password);
    await this.prisma.user.update({ where: { id: user.id }, data: { passwordHash } });
  }
  return user;
}
```

Is "Please verify your email first" an enumeration leak? Only after the attacker has proved they know the **correct password**, so it's acceptable.

Lesson 2 turns a verified user into a logged-in session.

## Upgrading hashes

`needsRehash` lets you make hashing stronger over time with no "everyone must reset their password" day. When a user logs in, you have their plain password for a moment, so you hash it again with the new settings.

The same trick moves you off an old algorithm. Say you join a company that used bcrypt:

```typescript
if (user.passwordHash.startsWith('$2')) {                       // bcrypt hashes start with $2a$, $2b$, $2y$
  ok = await bcrypt.compare(password, user.passwordHash);
  if (ok) await saveNewHash(await this.passwords.hash(password)); // now argon2id
}
```

Users who never log in again keep the old hash. After a year, you can force a password reset for just those accounts.

## Mistakes to avoid

- Hashing with SHA-256 or MD5, even with a salt. Too fast.
- Encrypting passwords "so support can see them". Support should never see them.
- Different error messages for "unknown email" and "wrong password".
- Returning early when the user doesn't exist (timing leak).
- Checking "does the email exist?" before inserting, instead of relying on the unique constraint.
- No maximum password length.
- Composition rules instead of a length and breached-password check.
- Logging the request body of `/auth/signup` or `/auth/login` (passwords in your logs).
- Comparing emails without normalising (`Rahim@Mail.com` vs `rahim@mail.com`).
- Treating `passwordHash = null` as "any password works" because of a bad `if`.

## Interview answer

**"How do you store passwords?"**

> "I never store the password itself, and I don't encrypt it, because encryption can be reversed. I hash it with a slow, salted password hashing algorithm. My choice is argon2id, which is the current OWASP recommendation, because it's also memory-hard, so GPU cracking is expensive. bcrypt is fine in existing systems. The salt and settings are stored inside the hash string, so I can raise the cost later and re-hash each user's password the next time they log in. I also limit the maximum password length, rate-limit the login endpoint because hashing is expensive, and check new passwords against a breached-password list instead of forcing symbols and numbers."

**"What is user enumeration and how do you prevent it?"**

> "It's when an attacker can find out whether an email has an account, for example because login says 'no such user', or because unknown emails answer faster since no password hash is checked. Attackers use that list for phishing and credential stuffing. To prevent it, I return the same message and status for every failure, verify against a dummy hash when the user doesn't exist so the timing is the same, and make sign-up and password reset always say 'check your email', with the email itself telling the user what happened."
