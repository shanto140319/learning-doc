## Lesson 1: Passwords and sign-up

**1.1**

```typescript
// scripts/hash-bench.mts (the .mts extension allows top-level await) — run with: npx tsx scripts/hash-bench.mts
import * as argon2 from 'argon2';

async function bench(label: string, options: argon2.Options): Promise<void> {
  await argon2.hash('warm-up', options);
  const start = performance.now();
  for (let i = 0; i < 20; i++) await argon2.hash('correct horse battery staple', options);
  console.log(label, ((performance.now() - start) / 20).toFixed(1), 'ms');
}

await bench('19 MiB, t=2', { type: argon2.argon2id, memoryCost: 19_456, timeCost: 2, parallelism: 1 });
await bench('64 MiB, t=3', { type: argon2.argon2id, memoryCost: 65_536, timeCost: 3, parallelism: 1 });
```

Typical results on a laptop: about 20–40 ms and 80–150 ms. For a 1 GB server with up to 10 logins per second: 10 × 64 MiB is 640 MiB at the worst moment, too close to the limit next to Node and Postgres connections. **Choose 19 MiB, t=2** (OWASP's minimum), maybe raise `timeCost` to 3, and protect the endpoint with rate limits. The reason in one sentence: "Memory per hash times concurrent logins must fit comfortably in RAM, so on a small server I keep memory at OWASP's minimum and rely on rate limiting."

**1.2** The migration, after `prisma migrate dev --create-only`:

```sql
-- generated by Prisma: create type role, create table users, memberships ...
alter table users add constraint users_email_lowercase check (email = lower(email));
alter table users add constraint users_name_length check (length(name) between 1 and 100);
```

```sql
insert into users (email, name) values ('Rahim@Test.dev', 'Rahim');
-- ERROR: new row violates check constraint "users_email_lowercase"
insert into users (email, name) values ('rahim@test.dev', 'Rahim');   -- OK
insert into users (email, name) values ('rahim@test.dev', 'Rahim 2'); -- ERROR: duplicate key (users_email_key)
```

The check plus the normal unique index together give "case-insensitive unique", because every stored value is already lowercase. For the controller: `@Public() @Post('signup') @HttpCode(202)` returning `{ message: 'Check your email to continue' }` in both branches.

**1.3** Typical results with the dummy hash: existing ≈ 35 ms, unknown ≈ 35 ms. Without it (returning early when the user is null): existing ≈ 35 ms, unknown ≈ 3 ms. Ten times faster is easy to measure over the internet, so an attacker can check a list of emails in minutes without triggering anything that looks like a failed password guess. Note: with network noise you may need more than 20 requests, but attackers have time.

**1.4**

```typescript
async changePassword(user: SessionUser, dto: ChangePasswordDto): Promise<void> {
  const current = await this.prisma.user.findUniqueOrThrow({ where: { id: user.id } });
  if (!current.passwordHash) {
    // Google-only account: there is no current password. Send them to "set a password" via the reset flow
    throw new BadRequestException('Your account has no password. Use "Forgot password" to set one.');
  }
  if (!(await this.passwords.verify(current.passwordHash, dto.currentPassword))) {
    throw new BadRequestException('Current password is incorrect');   // 400, not 401: they ARE logged in
  }
  if (dto.currentPassword === dto.newPassword) throw new BadRequestException('The new password must be different');
  if (await isBreachedPassword(dto.newPassword)) throw new BadRequestException('This password has appeared in a data breach.');

  const passwordHash = await this.passwords.hash(dto.newPassword);
  await this.prisma.$transaction(async (tx) => {
    await tx.user.update({ where: { id: user.id }, data: { passwordHash } });
    await tx.session.updateMany({                                      // log out other devices, keep this one
      where: { userId: user.id, revokedAt: null, id: { not: user.sessionId } },
      data: { revokedAt: new Date(), revokedReason: 'password_changed' },
    });
  });
  // + "your password was changed" email (Lesson 4) and an audit event (Lesson 9)
}
```

Rate-limit this endpoint too: it's another place to guess the current password if someone finds an open session.

## Lesson 2: Sessions, JWT and cookies

**2.1** Anyone can read `sub` (user ID), `sid` (session ID), `iat`, `exp`, `iss` and `aud`. After changing a character in the payload, `/v1/me` returns 401. The **signature** caught it: the server recomputes HMAC-SHA256 over `header.payload` and the result no longer matches the third part. (If you changed a character in the signature itself, the same thing happens.)

**2.2** In DevTools → Application → Cookies you should see `access_token` with the HttpOnly and Secure boxes ticked, SameSite `Lax`, and an expiry 15 minutes ahead. `document.cookie` in the console returns an empty string (or only non-httpOnly cookies). If the cookie doesn't appear at all, the usual causes are: the frontend and API on different sites without the proxy, or `fetch` without `credentials: 'include'` on a cross-origin call.

**2.3**

```typescript
// scripts/bad-tokens.mts
import jwt from 'jsonwebtoken';

const good = { sub: '<your user id>', sid: '<your session id>', iss: 'booking-api', aud: 'booking-web' };
const secret = process.env.JWT_SECRET!;

const tokens = {
  wrongSecret: jwt.sign(good, 'x'.repeat(32), { algorithm: 'HS256', expiresIn: '15m' }),
  algNone: `${Buffer.from(JSON.stringify({ alg: 'none', typ: 'JWT' })).toString('base64url')}.${Buffer.from(
    JSON.stringify({ ...good, exp: Math.floor(Date.now() / 1000) + 900 }),
  ).toString('base64url')}.`,
  expired: jwt.sign({ ...good, exp: Math.floor(Date.now() / 1000) - 60 }, secret, { algorithm: 'HS256' }),
  wrongAudience: jwt.sign({ ...good, aud: 'booking-mfa' }, secret, { algorithm: 'HS256', expiresIn: '15m' }),
};

for (const [name, token] of Object.entries(tokens)) {
  const res = await fetch('http://localhost:3000/v1/me', { headers: { cookie: `access_token=${token}` } });
  console.log(name, res.status);                  // all 401
}
```

| Token | Stopped by |
| --- | --- |
| Wrong secret | `secret` (signature check) |
| `alg: none` | `algorithms: ['HS256']` |
| Expired | `exp` is always checked (no option needed; don't turn on `ignoreExpiration`) |
| `aud: 'booking-mfa'` | `audience: 'booking-web'` |

**2.4** A good note covers: (1) **hybrid**: 15-minute JWT access token + Postgres session + rotating refresh token, because of fast checks with revocable sessions; (2) both tokens in httpOnly, Secure cookies, `Lax` / `Strict`, refresh limited to `/v1/auth`, because XSS can't steal them; (3) the Next.js `/v1` rewrite, so the API is same-origin: cookies work, server components can forward them, no CORS; (4) what you gave up: up to 15 minutes of access after logout. Typical interviewer follow-ups: "How does a server component refresh an expired token?", "What happens with two tabs?", "How would a mobile app authenticate?"

## Lesson 3: Refresh tokens and logout

**3.1**

```text
login        → T1 (unused)
refresh (T1) → T1 used, T2 created
refresh (T2) → T2 used, T3 created          the user holds T3
attacker sends T2 → T2 is used, and long ago (beyond the grace period) → REUSE → session revoked

Table: T1 used, T2 used, T3 unused — but the session is revoked, so T3 is dead too.
The attacker gets 401. The user's next refresh with T3 gets 401 → login page.
```

**3.2** For manual testing, set `expiresIn: '30s'` in `signOptions` and `maxAge: 30_000` in `setAccessCookie`. After 30 seconds, `GET /v1/me` → 401; `POST /v1/auth/refresh` → 204 with two new `Set-Cookie` headers; `GET /v1/me` → 200. Put the values back to 15 minutes afterwards (better: read them from config).

**3.3**

```typescript
// src/auth/errors.ts
export class RefreshInProgressError extends UnauthorizedException {
  constructor() { super('Refresh already in progress'); }
}

// in SessionsService.refresh, the switch:
case 'grace':
  throw new RefreshInProgressError();

// in the controller
try {
  setAuthCookies(res, await this.sessions.refresh(raw));
} catch (err) {
  if (!(err instanceof RefreshInProgressError)) clearAuthCookies(res);   // keep the winning tab's new cookies
  throw err;

```

The `api()` wrapper from Lesson 3 sends the user to the login page when a refresh fails. Change it: if the refresh returns 401 with the title "Refresh already in progress", wait 200 ms and retry the original request once (by then the cookie jar has the new tokens from the other tab).

**3.4**

```typescript
// scripts/reuse-attack.mts
const BASE = 'http://localhost:3000/v1';

const first = await refresh(r1);
const r2 = cookieOf(first, 'refresh_token')!;
console.log('first refresh', first.status);                         // 204

await new Promise((resolve) => setTimeout(resolve, 11_000));
```

## Lesson 4: Email verification, password reset and invites

**4.1**

- (a) **Guessable token.** The user ID may be known and the time can be guessed to within seconds, so an attacker can forge reset links for any account. Use 32 random bytes.
- (b) **Token in the query string.** The full URL, token included, goes to Google Analytics, to any third-party script in the `Referer` header, and to server logs. Anyone with access to those can reset the password. Use the fragment, `Referrer-Policy: no-referrer`, and no third-party scripts on token pages.
- (c) **Expiry too long.** Old emails in a hacked or shared inbox still work for a week. Use 30–60 minutes.
- (d) **Host header injection.** An attacker requests a reset for the victim's email with `Host: evil.com`; the victim receives a real email from you with a link to evil.com; if they click, the attacker receives the token. Build links from `APP_URL`.

**4.2** All failures go through `consume` returning `null` and the same `BadRequestException('This link is invalid or has expired')`. The old-link case fails because `create` deletes unused tokens of the same purpose. Using a verify token on the reset endpoint fails because of `purpose = ${purpose}` in the update.

**4.3**

```typescript
const accept = () => fetch(`${BASE}/invitations/accept`, {
  method: 'POST',
  headers: { 'content-type': 'application/json', cookie: inviteeCookies, origin: APP_ORIGIN },
  body: JSON.stringify({ token }),
});
const statuses = await Promise.all([accept(), accept()]).then((rs) => rs.map((r) => r.status));
console.log(statuses);     // [200, 400] in some order
```

```sql

```

The `updateMany ... where acceptedAt: null` claim decides the winner. The loser's `count` is 0, it throws, and its transaction rolls back.

**4.4** Typical numbers: with `await`, existing ≈ 40–80 ms (token insert + SMTP to Mailpit), unknown ≈ 5 ms. In the background: both ≈ 5–10 ms.

```typescript
// background send: never let an email error become an unhandled rejection
void this.emails.sendPasswordReset(user.email, user.name, token).catch((err: unknown) =>
  this.logger.error({ err, userId: user.id }, 'Password reset email failed'),
);
```

What an attacker learns from the first version: which emails have accounts, using an endpoint that **never** shows an error and that most teams don't monitor. With a real email provider (100–500 ms), the difference is even bigger.

## Lesson 5: Google login

**5.1**

- **Without `state`:** login CSRF. The attacker starts a Google login with their own account, stops before the callback, and sends you the callback link with their `code`. You visit it and are now logged in to **their** account; anything you add (a card, documents) goes to them.
- **Without `nonce`:** an ID token captured from an earlier login (a log, a proxy) could be replayed into a new login flow. The nonce ties each ID token to one attempt.
- **Without PKCE:** an attacker who steals the `code` from the redirect URL (browser history, a malicious extension, a log) can exchange it for tokens. With PKCE, they'd also need the `code_verifier`, which never left your server and the signed cookie.

**5.2** The state cookie parser:

```typescript
import { z } from 'zod';

const LoginStateSchema = z.object({
  state: z.string().min(1),
  nonce: z.string().min(1),
  codeVerifier: z.string().min(43),
  returnTo: z.string(),
});

export function parseLoginState(raw: unknown): GoogleLoginState | null {
  if (typeof raw !== 'string') return null;     // missing, or `false` when the signature check failed
  try {
    const parsed = LoginStateSchema.safeParse(JSON.parse(raw));
    return parsed.success ? { ...parsed.data, returnTo: safeReturnTo(parsed.data.returnTo) } : null;
  } catch {
    return null;
  }
}
```

The third linking case in `psql`:

```sql
select email, password_hash, email_verified_at from users where email = 'test@gmail.com';
-- password_hash: null, email_verified_at: set
select revoked_reason from sessions where user_id = '<id>';   -- account_claimed_by_email_owner
select provider, provider_user_id from user_identities where user_id = '<id>';
```

**5.3**

| `returnTo` | Result |
| --- | --- |
| `/bookings` | `APP_URL/bookings` |
| `//evil.com` | `/dashboard` (starts with `//`) |
| `/\evil.com` | `/dashboard` (browsers treat `\` like `/`, so it would be `//evil.com`) |
| `https://evil.com` | `/dashboard` (doesn't start with `/`) |
| `javascript:alert(1)` | `/dashboard` |
| `/%2F%2Fevil.com` | `APP_URL/%2F%2Fevil.com`: a 404 page on **your** site, which is safe. `new URL(value, appUrl)` keeps the host |

Changing `state` by one character: `authorizationCodeGrant` throws because `expectedState` doesn't match, and the catch redirects to `/login?error=google`. The cookie was already cleared, so the attempt can't be retried with the same state.

**5.4**

```typescript
async unlinkGoogle(userId: string): Promise<void> {
  await this.prisma.$transaction(async (tx) => {
    const user = await tx.user.findUniqueOrThrow({ where: { id: userId }, include: { identities: true } });
    const google = user.identities.find((i) => i.provider === 'google');
    if (!google) throw new NotFoundException('Google is not linked');

    const otherWays = (user.passwordHash ? 1 : 0) + user.identities.filter((i) => i.provider !== 'google').length;
    if (otherWays === 0) throw new ConflictException('Set a password before removing Google, or you will be locked out');

    await tx.userIdentity.delete({
      where: { provider_providerUserId: { provider: 'google', providerUserId: google.providerUserId } },
    });
  });
}
```

Build vs buy note (example): "For Project 1 I built authentication myself, because it's a portfolio project and I wanted to understand sessions, refresh rotation and OAuth in depth. For a real product, I'd compare three options. A hosted provider like Clerk or WorkOS is fastest and gives enterprise SSO, but costs money per user and keeps user data outside our database. A library like Better Auth keeps users in our Postgres and our code, with less to write ourselves. Building it ourselves gives full control but we own every security fix. For a small B2B SaaS that needs SAML soon, I'd lean towards a hosted provider; otherwise Better Auth."

**6.4** Leave the business:

```typescript
async leave(actor: AuthUser): Promise<void> {
  await this.prisma.$transaction(async (tx) => {
    const owners = await tx.$queryRaw<{ user_id: string }[]>`
      select user_id from memberships
      where business_id = ${actor.businessId}::uuid and role = 'owner'
```

## Lesson 7: Browser security

**7.1**

- (a) **XSS** (stored): an admin writes a description with a script; every visitor runs it. Render as text, or sanitise with DOMPurify.
- (b) **CSRF**: a `GET` that changes state can be triggered by an `<img src=...>` or a link, and `SameSite=Lax` cookies are sent on top-level `GET`s. Make it `POST`.
- (c) **CORS** misconfiguration: any website can read logged-in users' API responses. Use an exact origin list.
- (d) **Safe**: React escapes it.
- (e) **Clickjacking**: the settings page can be framed and the user tricked into clicking. Add `frame-ancestors 'none'`.

**7.2** Without CSP, `dangerouslySetInnerHTML` shows an alert with your domain. With the CSP, the console shows something like: *Refused to execute inline event handler because it violates the following Content Security Policy directive: "script-src 'self' 'nonce-...' 'strict-dynamic'"*. Inline event handlers (`onerror=`) have no nonce, so they never run. The image still breaks, but no code runs. That's the "second layer" working; the first layer (not using `dangerouslySetInnerHTML`) is still the real fix.

**7.3** `evil.html`:

```html
<form id="f" action="http://localhost:3001/v1/auth/logout" method="POST"></form>
<button onclick="document.getElementById('f').submit()">Logout form</button>
<button onclick="fetch('http://localhost:3001/v1/bookings/<id>/cancel', { method: 'POST', credentials: 'include' }).then(r => console.log(r.status))">Fetch cancel</button>
```

- The form: `localhost:5000` and `localhost:3001` are the **same site** (ports don't count for sites), so `SameSite=Lax` doesn't block the cookie here. **`OriginGuard`** blocks it (`Origin: http://localhost:5000` isn't allowed) → 403. This is exactly the "sibling site" case.
- The fetch: also 403 from `OriginGuard`. (It would be blocked by the CORS preflight only if it used JSON or custom headers; this one is a "simple" request, so it **is** sent.)
- Without `SameSite`: the same result, because `OriginGuard` and `Sec-Fetch-Site` don't depend on cookies' attributes. Layers working.

**7.4** Common violations: inline `<script>` from an analytics snippet (move to `next/script` with the nonce), inline `style` attributes from a UI library (add the nonce, or as a last resort `'unsafe-inline'` for **styles only**, which is much less dangerous than for scripts), fonts from Google Fonts (`font-src https://fonts.gstatic.com` and `style-src https://fonts.googleapis.com`; better, use `next/font`, which self-hosts them), images from a CDN (`img-src`), and Stripe.js (add the domains from Stripe's CSP docs).

## Lesson 8: Abuse, webhooks, API keys and secrets

**8.1**

| Feature | Main risk | Example limit |
| --- | --- | --- |
| Sign-up | Fake accounts, email spam from your domain | 5 per IP per hour; CAPTCHA if abused |
| Login | Brute force, credential stuffing, argon2 CPU/RAM | 10 per IP per minute, 10 per email per 15 minutes |
| Forgot-password | Email bombing a victim, enumeration by timing | 3 per IP per hour, 3 per email per hour |
| Invite | Spam to any address from your domain | 20 per business per day |
| Public booking creation | Fake bookings that block slots | 10 per IP per hour; email confirmation for new customers |
| CSV export | Heavy queries, data scraping | 5 per user per hour; audit-logged |
| Import from URL | SSRF, slow or huge responses | 10 per business per hour; SSRF checks, 5 s timeout, 1 MB max |

**8.2** The per-email part: after 10 attempts for `owner@test.dev`, the 11th gets 429 with `Retry-After` (seconds until the window ends). In the second case, 15 different emails are 15 different trackers for the email guard, but the **per-IP** limit (10/min) still stops request 11. A real credential-stuffing attack uses thousands of IPs, though, so each IP stays under the limit and each email gets only one or two tries. What else stops it: breached-password checks (fewer reused passwords), CAPTCHA after failures, 2FA, new-login emails, and monitoring the overall failed-login rate (an alert when it jumps).

**8.3**

| URL | Result | String check would miss it? |
| --- | --- | --- |
| `https://example.com` | allowed | |
| `http://example.com` | rejected (not https) | |
| `https://127.0.0.1` | rejected (loopback) | no |
| `https://[::1]` | rejected: `hostname` is `[::1]` with brackets, so `lookup` fails. Strip brackets if you want a clear error message | yes, if it only checks `localhost` and `127.` |
| `https://169.254.169.254` | rejected (link-local) | yes, if the list only has `localhost` and `127.0.0.1` |
| `https://localhost` | rejected (resolves to `127.0.0.1` / `::1`) | no |
| `https://user:pass@example.com` | rejected (credentials) | |
| `https://localtest.me` | rejected (resolves to `127.0.0.1`) | **yes**: it looks like a normal public domain |

```typescript
const body = JSON.stringify({ id: 'evt_1', type: 'test' });
```

**9.4** The checks inside `verify`:

```typescript
async verifyTotp(userId: string, code: string): Promise<boolean> {
  const user = await this.prisma.user.findUniqueOrThrow({ where: { id: userId } });
  if (!user.totpEnabledAt || !user.totpSecretEncrypted) return false;
  const secret = this.encryptor.decrypt(user.totpSecretEncrypted);

  const now = Math.floor(Date.now() / 30_000);
  for (const step of [now - 1, now, now + 1]) {
    if (!timingSafeEqualStrings(totpFor(secret, step), code)) continue;
    // Only accept steps newer than the last used one, in one atomic update (no double use, even in parallel)
    const updated = await this.prisma.user.updateMany({
      where: { id: userId, OR: [{ totpLastStep: null }, { totpLastStep: { lt: BigInt(step) } }] },
      data: { totpLastStep: BigInt(step) },
    });
    return updated.count === 1;
  }
  return false;
}
```

(`totpFor` is your library's function for "the code at this time step", and `timingSafeEqualStrings` is a small helper that compares two strings with `timingSafeEqual` after checking their lengths.) Attack results: same code twice → second fails (`totpLastStep`); code from 2 minutes ago → fails (outside ±1 step); `mfaToken` as `access_token` cookie → 401 (wrong audience); recovery code twice → second fails (`usedAt` set by an atomic `updateMany ... where usedAt: null`); 10 wrong codes → 429 after the limit, and the `mfaToken` should become useless after 5 failures (count failures per `mfaToken` ID in a table or in Redis later).
